The branch menu decides, from the card itself, what the workflow does when a step gets an error. It opens from the rows of **On failure** and has one option per thing the workflow can do: a new step, a jump to a later step, end, retry, or remove what is there.

## Example: retry a 404 of getWeakness

<Steps>
1. Open **Pokemon card** and click the **Design** tab.
2. On the card of `getWeakness`, find the row `404 → no action` **fails**.
3. Click the **+** at the end of the row. A menu opens, titled **If it responds 404**.
4. Click **Retry (up to 3 times)**.
</Steps>

<Tabs>
<TabItem label="On the card">

The row now reads `404 → on404` **retries ×3**. The **+** has become a pencil.

</TabItem>
<TabItem label="In the YAML">

```yaml title="pokemon.arazzo.yaml" {3-9}
- stepId: getWeakness
  # …
  onFailure:
    - name: on404
      type: retry
      retryAfter: 1
      retryLimit: 3
      criteria:
        - condition: $statusCode == 404
```

</TabItem>
</Tabs>

## Open the menu

The rows are in the section **On failure** of each card. **Actions by response**, above the canvas, must be on to see them. It is on by default.

| Row | Button at the end | Tooltip |
|---|---|---|
| A documented error with no action: `404 → no action` **fails** | **+** | **What to do if it responds 404** |
| A status with an action: `404 → on404` **end ✕** | A pencil | **Change what to do if it responds 404** |
| A status the contract does not document | **+ If it responds another status…**, at the end of the section | See [Statuses the contract doesn't document](/design/branch-other-status/) |

The menu opens below the button. It closes when you choose an option, press **Esc**, click outside it or scroll the canvas.

![The card of getProduct with the row 404 → no action fails and its + menu open: If it responds 404, + A new step…, Go to “Create order”, End the workflow and Retry (up to 3 times)](/media/en/design-branch-menu.webp)

Some rows have no button:

- A row that groups several statuses, or one with no status, such as `other error`.
- A row of `onSuccess`, such as `success → done` **end ✓**.
- Any row of a step that calls another workflow, of a messaging step or of a step whose operation is not in a contract.

Edit those in the [YAML tab](/design/arazzo-editor/).

## The options, one by one

The menu lists its options in this order. Each option except **+ A new step…** is a single change: **Undo** above the canvas, or ⌘Z (Ctrl+Z), reverts it.

### + A new step…

Adds a step that runs only for this response and connects it to the branch. It opens a dialog with the palette, puts the step at the end of the workflow and ends the happy path before it. It is the first option and has the focus when the menu opens.

Read [A new step for an error](/design/branch-new-step/) for the whole flow.

### Go to “step”

One option per step that comes **after** this one, with its name in words: for `getWeakness`, the menu of `getSpecies` shows **Go to “Get weakness”**. The last step of a workflow has none.

The run jumps to that step and goes on from there, skipping the steps in between.

```yaml {3-5}
onFailure:
  - name: on404
    type: goto
    stepId: getWeakness
    criteria:
      - condition: $statusCode == 404
```

The row reads `404 → on404` **go to getWeakness**, and an orange dashed line runs along the left from the row to the card of `getWeakness`.

To jump to an earlier step, for example to poll until something is ready, use the step panel: its list offers every other step of the workflow. A loop that runs more than 200 steps stops with **The run was stopped: possible infinite loop of goto/retry actions.**

### End the workflow

The run stops at this step as a known outcome. The steps below do not run.

```yaml {3}
onFailure:
  - name: on404
    type: end
    criteria:
      - condition: $statusCode == 404
```

The row reads `404 → on404` **end ✕**. In the results, the step shows **↪ End of workflow (action "on404")**.

### Retry (up to 3 times)

The run calls the step again. The menu always writes the same defaults:

| Field | Value | Meaning |
|---|---|---|
| `retryAfter` | `1` | Seconds to wait before each try. With the real API, Luvin never waits more than 10 seconds. In Simulation it does not wait. |
| `retryLimit` | `3` | Tries after the first call. If all fail, the step fails and the results say **The 3 retries were exhausted**. |

The row reads `404 → on404` **retries ×3**. To use other numbers, change them in the YAML tab, or save the action as a [reusable](/design/reusables/), whose panel has both fields. See [Retries and slow calls](/design/success-and-errors/#retries-and-slow-calls).

### Remove the branch

Shows only when the status already has an action. It removes the action named `on404`. If the step has no other action on failure, `onFailure` goes away too. The row goes back to `404 → no action` **fails**, or disappears if the contract does not document that status.

It does not remove a step created with **+ A new step…**, nor the `done` that came with it. See [Remove a branch to a new step](/design/branch-new-step/#remove-a-branch-to-a-new-step).

## Change a branch

<Steps>
1. Click the pencil of the row. The same menu opens, now with **Remove the branch** at the end.
2. Choose another option.
</Steps>

Luvin replaces the action `on404` in its place in the list, so its position does not change.

## The menu and the step panel

Both write the same action. Each one has something the other does not:

| | Card menu | Step panel |
|---|---|---|
| Where | **On failure**, on the card | **If it responds with an error**, in the panel |
| A new step for the error | **+ A new step…** | No |
| Go to | Only later steps | Any other step, earlier ones too |
| Reusable actions | No | A **Reusables** group, when one handles that status |
| Statuses the contract does not document | **+ If it responds another status…** | Only those that already have an action |
| No action | **Remove the branch** | **No action (the workflow fails)** |

## Troubleshooting

**Two rows for the same status.** The menu and the panel write and remove only the action named `on` plus the status. If the status was handled by an action with another name, such as `pokemonNotFound` in `getPokemon`, choosing an option adds `on404` after it, and **Remove the branch** leaves it in place. The run uses the first action of the list that matches, so `pokemonNotFound` still wins. Change or delete the other action in the YAML tab.

**The row has no + or pencil.** See the list in [Open the menu](#open-the-menu). Check also that you are in the **Design** tab: the diagram of the **Overview** tab only shows the branches.

**The menu has no Go to option.** The step is the last one, so there is no later step. Use the step panel to jump to an earlier one.

<Aside type="tip">
Each branch also gets a generated case that simulates that response, for example **getWeakness responds 404 → on404**. Run it to check the branch without making the API fail. See [Cases](/test/cases/).
</Aside>
