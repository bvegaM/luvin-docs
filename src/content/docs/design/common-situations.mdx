This page answers "how do I…?" for the situations people meet most when they design a workflow. Each one has the situation in one line, how to do it in the **Design** tab, what Luvin writes in the Arazzo file, and the page that explains it in full.

The examples use the Pokédex example of the app and a generic shop: log in, list products, create an order and read it back.

<Aside type="tip" title="Canvas or YAML">
Most situations are done on the canvas. A few, such as criteria on the body or actions on success, are written in the [YAML tab](/design/arazzo-editor/). Each situation says which one. Whatever you write by hand is kept when you go back to the canvas.
</Aside>

## Pass data from one step to the next

### A token from the login goes in a header of the next steps

The login returns `accessToken`, and the next calls need `Authorization: Bearer <token>`.

<Steps>
1. Click the `login` step. Under **Outputs**, tick `accessToken`. The card now shows the output `token`.
2. Click the step that needs the token, for example `createOrder`.
3. Under **Parameters** › **Headers**, open the **Source** list of `Authorization` and choose **Fixed value…**.
4. Type `Bearer {$steps.login.outputs.token}`. The braces mark an expression inside a text.
5. Do the same in each later step that needs the token.
</Steps>

You should see the text in the field and, on the card, the value `Bearer {$steps.login.outputs…`.

![The step panel of createOrder: the Authorization header with a fixed value that contains the token of the login step](/media/en/design-token-header.webp)

```yaml
- stepId: login
  outputs:
    token: $response.body#/accessToken
- stepId: createOrder
  parameters:
    - name: Authorization
      in: header
      value: Bearer {$steps.login.outputs.token}
```

The canvas draws no data line for a value written inside a text: the line is only drawn when the whole value is the output. The header only appears in the panel if the contract declares it. If it does not, add the parameter in the YAML tab. To send the token without writing it in each step, use the [authorization of the workflow](/authorization/workflow/) instead. Runnable example: [Log in and use the token](/recipes/login-token/).

### An id from a response goes in the path of the next step

You add `GET /pokemon-species/{idOrName}` after `GET /pokemon/{idOrName}`, and the second needs the `id` of the first.

<Steps>
1. Add the two operations with **+** or by dragging them onto the canvas.
2. Look at the second card. Its `idOrName` shows `? getPokemon › id`: Luvin connected it for you and added the output `id` to the first step.
3. If the source is not the one you want, click the step and choose another one in its **Source** list.
</Steps>

![A new workflow with two steps: Start has the input idOrName, the first step reads it and exposes id](/media/en/design-auto-wired.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-wire.webp" src="/media/en/design-wire.mp4"></video>

```yaml
- stepId: getPokemonSpecies
  parameters:
    - name: idOrName
      in: path
      value: $steps.getPokemon.outputs.id
```

The `?` means Luvin is less sure: review it. Details: [Connect data between steps](/design/wire-data/).

### A value nobody provides becomes an input

When no earlier step returns a value the step needs, Luvin creates an input of the workflow with the name of the value. In the image above, **Start** lists `idOrName`, created when you added the first step.

To do it yourself, open the **Source** list of the value and choose **New input “name”**. The input is created as required.

```yaml
inputs:
  type: object
  required: [idOrName]
  properties:
    idOrName: { type: string }
steps:
  - stepId: getPokemon
    parameters:
      - { name: idOrName, in: path, value: $inputs.idOrName }
```

You fill the inputs in the **Inputs** tab. See [Inputs](/test/inputs/).

### A fixed value becomes an input, and back

A step sends `currency: EUR` always. You want cases that try other currencies.

<Steps>
1. On the card, point at the fixed value. **→ input** appears next to it.
2. Click **→ input**. **Start** gets the input `currency`, with `EUR` as its value, and the step reads it.
3. To pick several at once, click **+ Turn another fixed value into an input** on **Start** (or **Choose variable data…** when there are no inputs yet), tick the values in **Data to vary per case** and click **Turn into inputs**.
</Steps>

![The createOrder card with the → input button next to the fixed value of currency](/media/en/design-promote-one.webp)

![The Data to vary per case dialog with two values ticked: currency and address/city](/media/en/design-pick-data.webp)

To go back, there is no single button. Do it in two moves:

<Steps>
1. Click the step and, in the **Source** list of the value, choose **Fixed value…**. Type the value. The field stays in view while you edit it, also when it is optional.
2. Click **Start** and delete the input with its bin.
</Steps>

If you delete an input that a step still uses, the bar **This workflow is missing data** appears. Right after turning values into inputs, **Undo** also brings back the fixed values.

<video controls muted playsinline preload="metadata" poster="/media/en/design-promote.webp" src="/media/en/design-promote.mp4"></video>

```yaml
inputs:
  properties:
    currency:
      type: string
      description: createOrder · body · currency
      example: EUR
steps:
  - stepId: createOrder
    requestBody:
      payload:
        currency: $inputs.currency
```

Details: [Parameters and body](/design/parameters-and-body/#turn-a-fixed-value-into-an-input).

### A field that comes from a list

`listProducts` returns `items`, a list, and the next step needs the `sku` of one product.

<Steps>
1. Click the next step and open the **Source** list of the value.
2. Under `listProducts`, choose **items/sku (from a list: you choose which at run time)**.
</Steps>

The field is shown without its position: `items/sku`. In the file Luvin writes the first position, and when you run a case it pauses after the step and asks which item to continue with. The outputs panel also lets you expose the **whole list**.

![The outputs of listProducts: the note about the list, the whole list tag and items/sku ticked](/media/en/design-list-outputs.webp)

```yaml
- stepId: listProducts
  outputs:
    sku: $response.body#/items/0/sku
```

Details: [Outputs](/design/outputs/#fields-that-are-lists) and [Choose an item from a list](/test/lists/).

### Nested objects and lists in a body

The order has an `address` object and a list of `lines`.

<Steps>
1. Click the step. Under **Body**, fields inside objects appear with their path: `address/city`, `address/zip`. Give each one a source.
2. For the list, click **Edit as JSON**, write the items and click **Apply**. Use `"$inputs.name"` or `"$steps.step.outputs.value"` as values.
</Steps>

![The Edit as JSON box of createOrder with the address object and the lines list](/media/en/design-body-json.webp)

```yaml
requestBody:
  contentType: application/json
  payload:
    customer: Ana
    address: { city: Madrid, zip: '28001' }
    lines:
      - { sku: $steps.listProducts.outputs.sku, qty: 1 }
```

Details: [Parameters and body](/design/parameters-and-body/#edit-the-body-as-json).

### The same operation twice in one workflow

You want to read a Pokémon, and later another one. Add the same operation again from the palette. The new step gets a number: `getPokemon2`. Each step has its own parameters and outputs, so later steps can read `$steps.getPokemon.outputs…` or `$steps.getPokemon2.outputs…`.

```yaml
- stepId: getPokemon
  operationId: $sourceDescriptions.pokeapi.getPokemon
- stepId: getPokemon2
  operationId: $sourceDescriptions.pokeapi.getPokemon
```

To give it a clearer name, click the step and change its name at the top of the panel. Details: [Add steps](/design/add-steps/).

## Change the order or undo

### Reorder, delete, undo and redo

<Steps>
1. Point at a card and click **↑** or **↓**, or drag it above or below another card.
2. If the step now runs before the one that gives it data, the bar **Check the order:** says so. Click **Undo** in the bar.
3. To delete a step, click it and press Delete, or click the bin at the top of its panel. A red bar names the steps that used its data, and each of them shows **1 error(s)** on its card.
4. **Undo** and **Redo** above the canvas (⌘ + Z and ⇧ + ⌘ + Z) step through your changes.
</Steps>

![The Check the order bar: getOrder uses data from createOrder, which now runs after it](/media/en/design-order-warning.webp)

## Decide what counts as success

### Success by status

Click the step and, under **It's a success if it responds**, click the status you expect. Luvin writes `$statusCode == 201`.

### Success by a condition on the response

The canvas edits the status. Conditions on the body or the headers are written in the YAML tab, inside `successCriteria`. All the criteria must hold. The panel lists them under the status with **Edit in the YAML**.

| Kind | Example |
|---|---|
| Simple | `- condition: $response.body#/capture_rate >= 0` |
| Regex | `- context: $response.header.Content-Type`<br />`  condition: ^application/json`<br />`  type: regex` |
| JSONPath | `- context: $response.body`<br />`  condition: $.abilities[?(@.is_hidden == false)]`<br />`  type: jsonpath` |
| XPath (XML responses) | `- context: $response.body`<br />`  condition: /order/status`<br />`  type: xpath` |

![The panel of getSpecies: the success status and an extra criterion with Edit in the YAML](/media/en/design-criteria-panel.webp)

Details: [Success and errors](/design/success-and-errors/), [Success criteria](/reference/criteria/) and the recipe [Check more than the status](/recipes/criteria/).

## Decide what happens on an error

<video controls muted playsinline preload="metadata" poster="/media/en/design-errors.webp" src="/media/en/design-errors.mp4"></video>

### An expected error ends the workflow

"The Pokémon does not exist" is a known outcome, not a crash.

<Steps>
1. Click the step. Under **If it responds with an error**, find the status, for example **404**.
2. Open its list and choose **End the workflow**.
</Steps>

```yaml
onFailure:
  - name: on404
    type: end
    criteria:
      - condition: $statusCode == 404
```

Luvin also generates a case that simulates the 404 and checks that the action fires. Runnable example: [Expect an error](/recipes/expected-error/).

### Retry with a wait and a limit

Choose **Retry (up to 3 times)** for the status, for example **429**. Luvin writes 3 tries and 1 second between them. To change the numbers, edit `retryLimit` and `retryAfter` in the YAML tab, or save the action as a [reusable](/design/reusables/): its panel has both fields. Luvin never waits more than 10 seconds between two tries against the real API.

```yaml
onFailure:
  - name: on429
    type: retry
    retryAfter: 5
    retryLimit: 4
    criteria:
      - condition: $statusCode == 429
```

To log in again before the retry, add `stepId` or `workflowId` to the action in the YAML. See [Retries and slow calls](/design/success-and-errors/#retries-and-slow-calls).

### Jump to another step

Choose **Go to “step”** for the status. The list offers every other step of the workflow. With **Actions by response** on, the card shows the row and an orange line goes to the target step.

![The canvas: the 409 row of createOrder says go to listProducts and an orange dashed line runs up to that step](/media/en/design-jump-line.webp)

```yaml
onFailure:
  - name: on409
    type: goto
    stepId: listProducts
    criteria:
      - condition: $statusCode == 409
```

### Jump to another workflow

The list of the panel only offers steps. To continue in another workflow, write `workflowId` instead of `stepId` in the YAML. The run continues in that workflow, and the results say **Continues in workflow "…"**.

```yaml
onFailure:
  - name: notifySupport
    type: goto
    workflowId: reportProblem
    criteria:
      - condition: $statusCode == 500
```

For a workflow of another Arazzo file, use `$sourceDescriptions.<source>.<workflowId>`.

### Actions on success

`onSuccess` is written in the YAML. It takes the same types: `end`, `goto` and `retry`. The panel says **This step uses things the canvas doesn’t edit (onSuccess)**. The card lists the action in the same section as the error actions; an `end` on success reads **end ✓**.

```yaml
- stepId: findItem
  onSuccess:
    - name: done
      type: end
```

Runnable example: [Retry, jump and end on errors](/recipes/error-branches/).

## Keep values

### Outputs of a step and outputs of the workflow

<Steps>
1. Click the step. Under **Outputs**, tick the response fields you want. Each one appears on the card with a dot.
2. Click **End of workflow** and, under **Workflow outputs**, tick what the workflow returns. Click a name to change it.
</Steps>

![The End of workflow panel: the candidate outputs, with createOrder › orderId ticked and its name](/media/en/design-workflow-outputs.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-outputs.webp" src="/media/en/design-outputs.mp4"></video>

```yaml
- stepId: getOrder
  outputs:
    status: $response.body#/status
outputs:
  orderId: $steps.createOrder.outputs.orderId
```

## Use other workflows

### Depend on another workflow of the same file or of another file

`placeOrder` needs the token that the `login` workflow returns, and `login` is in `auth.arazzo.yaml`.

<Steps>
1. Click **Start**. Under **Depends on**, open **Add a workflow…**.
2. Choose a workflow under **In this file** or under the group of another file, such as **In auth.arazzo.yaml**.
3. A **Depends on** card appears above **Start** with the outputs of that workflow. Use them from the **Source** list of any value, or drag their dot.
</Steps>

![The Add a workflow list with the groups In this file and In auth.arazzo.yaml](/media/en/design-depends-options.webp)

![The Depends on card above Start: the login workflow of auth.arazzo.yaml and its output token](/media/en/design-depends-card.webp)

```yaml
sourceDescriptions:
  - { name: auth, url: ./auth.arazzo.yaml, type: arazzo }
workflows:
  - workflowId: placeOrder
    dependsOn: [$sourceDescriptions.auth.login]
```

For a workflow of the same file, `dependsOn` has only its id: `dependsOn: [browseProducts]`. Details: [Workflows that use other workflows](/design/dependencies/).

### Call a workflow as a step

In the palette, open **Workflows in this Arazzo** (or **From other Arazzo files**) and click **+** on the workflow. The new step lists the inputs of that workflow under **Workflow inputs**, wired like any other value, and its outputs.

![The panel of a step that calls the workflow browseProducts: its input limit and its outputs sku and price](/media/en/design-call-workflow.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-depends.webp" src="/media/en/design-depends.mp4"></video>

```yaml
- stepId: browseProducts
  workflowId: browseProducts
  parameters:
    - { name: limit, value: $inputs.limit }
  outputs:
    sku: $outputs.sku
    price: $outputs.price
```

## Define once, use in several steps

### Reusable failure actions and parameters

<Steps>
1. Set the action of an error, for example **Retry** on **429**, or give a parameter a value.
2. Click ♻ (**Save as reusable**) on that row, type a name and click **Save**.
3. In another step, the list of that status offers it under **Reusables**. You can also drag it from the **Reusables** group of the palette onto a card.
4. Click the ♻ badge to edit it once for every step. **Used in** lists the steps.
</Steps>

![The panel of the reusable unauthorized of PayPal: ends the workflow on a 401 and is used in five steps](/media/en/design-reusable-panel.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-reusables.webp" src="/media/en/design-reusables.mp4"></video>

```yaml
components:
  failureActions:
    tooManyRequests:
      name: tooManyRequests
      type: retry
      retryAfter: 1
      retryLimit: 3
      criteria:
        - condition: $statusCode == 429
# in each step:
onFailure:
  - reference: $components.failureActions.tooManyRequests
```

Details: [Reusables](/design/reusables/).

## Messages and events

### Send and receive messages

<Aside type="caution">
Messaging steps are always simulated. Luvin does not connect to brokers (Kafka, AMQP, MQTT…) yet: the step uses the examples of the AsyncAPI contract, also when you run against the real API.
</Aside>

Drag the AsyncAPI operation from the palette, as with any operation: it is tagged **SEND** or **RECEIVE**. Luvin writes `action`, the correlation id and, for a receive, `timeout: 5000`. Outputs are edited in the panel. Criteria on the message, such as the one below, are written in the YAML tab. See [Add a messaging step](/design/messaging/#add-a-messaging-step).

![The panel of awaitConfirmation, a receive step: it says the canvas does not edit its channel, correlation and timeout, and lists its criterion on the message and its output entryNumber](/media/en/design-messaging-receive.webp)

```yaml
- stepId: awaitConfirmation
  channelPath: '{$sourceDescriptions.pokedexEvents.url}#/channels/sightingConfirmed'
  action: receive
  correlationId: $inputs.correlationId
  timeout: 5000
  successCriteria:
    - condition: $message.payload#/status == 'CONFIRMED'
```

Details: [Messaging steps](/design/messaging/).

## Without a contract

### Build from saved requests

<Steps>
1. Create a workflow with **+** › **New Arazzo**.
2. In the palette, open **Collection requests** and add your requests with **+** or by dragging them.
3. The first time you use each request, mark what the API requires and click **Save**.
4. Click a step and **Try this step**, or run the workflow once against the real API, so Luvin learns the responses.
5. The bar **Luvin found 1 connection(s) between steps** proposes the connections. Click **Connect**.
</Steps>

![The bar Luvin found 1 connection(s) between steps: the orderId of getOrder would come from the id of createOrder](/media/en/design-connections-bar.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-from-requests.webp" src="/media/en/design-from-requests.mp4"></video>

Details: [Build from saved requests](/design/from-requests/).

### Mark the required fields of a request

A request does not say which fields the API requires. The dialog **What does the API require in «…»?** asks it the first time. To change it later, click the step and then **Required fields (n)** at the top of the panel.

![The dialog What does the API require in «Create order»? with customer ticked as required](/media/en/design-required-fields.webp)

```yaml title="requests/create-order.request.yaml"
requiredFields:
  - body:customer
```

Details: [Mark the required fields of a request](/design/required-fields/).

## Fix a workflow

### Complete the missing data

After a contract changes, or after you edit the YAML, a step may use an input the workflow does not declare, or not send something the contract requires. The bar **This workflow is missing data** says what. Click **Complete**. **Undo** reverts it.

![The bar This workflow is missing data: it uses inputs the workflow does not declare, username, with the Complete button](/media/en/design-gaps-bar.webp)

Details: [Complete missing data](/design/complete-gaps/).

### Edit the YAML by hand

<Steps>
1. Open the **YAML** tab. It is the same file the canvas edits.
2. Type. After `$`, `$steps.` or `$inputs.` the editor suggests what exists.
3. Check the badge above the text and the **Problems** list below it.
4. Go back to **Design**. What you wrote stays, also after you change other things on the canvas.
</Steps>
