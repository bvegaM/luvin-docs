Cada paso necesita dos decisiones: qué respuesta significa que salió bien, y qué hacer cuando la API responde con un error. Luvin define la primera a partir del contrato y deja la segunda a ti. Ambas están en el panel del paso, y la segunda también en la tarjeta del paso.

Esta página es el resumen. Para ver cómo avanza una ejecución de un paso a otro después de cada acción, lee [Ramas de error](/es/design/branches/).

## Ejemplo: un Pokémon que no existe

En **Pokemon card**, el primer paso termina el workflow cuando la API responde 404, así que «el Pokémon no existe» es un resultado conocido y no una falla inesperada.

<Tabs>
  <TabItem label="En la app">

  En el panel del paso `getPokemon`, **Es éxito si responde** tiene **200** seleccionado. Bajo **Si responde con error**, la lista junto a **404** dice **Terminar el workflow**. En el lienzo, con **Acciones según la respuesta** activado, la tarjeta muestra la fila `404 → pokemonNotFound` **fin ✕**.

  ![El panel de un paso con los outputs y la acción elegida para cada error documentado](/media/es/step-outputs.webp)

  </TabItem>
  <TabItem label="En el YAML">

```yaml title="pokemon.arazzo.yaml" {7-11}
- stepId: getPokemon
  successCriteria:
    - condition: $statusCode == 200
    - context: $response.body
      condition: $.abilities[?(@.is_hidden == false)]
      type: jsonpath
  onFailure:
    - name: pokemonNotFound
      type: end
      criteria:
        - condition: $statusCode == 404
```

  </TabItem>
</Tabs>

## Qué cuenta como éxito

<Steps>
1. En la pestaña **Diseño**, haz clic en un paso.
2. Busca **Es éxito si responde**. Tiene una opción por cada estado 2xx que el contrato documenta para la operación.
3. Haz clic en el estado que esperas.
</Steps>

Un paso nuevo parte con el 2xx documentado más bajo, o 200 si el contrato no documenta ninguno. En el archivo se escribe como `$statusCode == 200`. Cualquier otra respuesta hace fallar el paso.

### Más que el estado

Un paso también puede revisar el contenido de la respuesta. Estos criterios adicionales se escriben en la [pestaña YAML](/es/design/arazzo-editor/). El panel los lista debajo de los estados con el enlace **Editar en el YAML**, y la tarjeta los muestra bajo **Criterios de éxito**. Todos los criterios deben cumplirse a la vez.

En **Pokemon card**, el paso `getSpecies` revisa el estado y un campo:

```yaml title="pokemon.arazzo.yaml" {3}
successCriteria:
  - condition: $statusCode == 200
  - condition: $response.body#/capture_rate >= 0
```

Mira [Criterios JSONPath y regex](/es/recipes/criteria/) para ejemplos ejecutables.

![El panel de getSpecies: el status 200 elegido, el criterio extra $response.body#/capture_rate >= 0 y el enlace Editar en el YAML](/media/es/design-criteria-panel.webp)

## Qué pasa ante cada error

**Si responde con error** lista cada estado de error que el contrato documenta para la operación, con la descripción del contrato. Cada uno tiene una lista de acciones.

| Acción | Qué hace el workflow |
|---|---|
| **Sin acción (el workflow falla)** | Es la predeterminada. El paso falla y el workflow se detiene con una falla genérica. |
| **Terminar el workflow** | Se detiene en este paso como un resultado conocido, por ejemplo «el Pokémon no existe». |
| **Reintentar (hasta 3 veces)** | Llama al paso otra vez, hasta 3 veces, esperando 1 segundo antes de cada intento. Si sigue fallando, el workflow falla. |
| **Ir a «paso»** | Salta a otro paso del workflow y continúa desde ahí. |

Puedes elegir la acción desde la tarjeta en el lienzo o desde el panel del paso. Las dos escriben lo mismo en el archivo.

### Desde la tarjeta

En la pestaña **Diseño**, cada tarjeta tiene una sección **Si falla** con una fila por cada estado de error que documenta el contrato. Para ver las filas, **Acciones según la respuesta**, sobre el lienzo, tiene que estar activado. Viene activado.

| La fila muestra | Botón al final de la fila |
|---|---|
| `404 → sin acción` **falla** | **+**. Su tooltip dice **Qué hacer si responde 404**. |
| `404 → on404` **fin ✕**, u otra acción | Un lápiz. Su tooltip dice **Cambiar qué hacer si responde 404**. |

Haz clic en el botón y elige en el menú **Si responde 404**: **+ Un paso nuevo…**, **Ir a «Get weakness»** (solo pasos posteriores), **Terminar el workflow**, **Reintentar (hasta 3 veces)** o, cuando el estado ya tiene una acción, **Quitar la rama**. Para un estado que el contrato no documenta, usa **+ Si responde otro status…**, al final de la sección.

Cada opción se explica en [El menú de una rama](/es/design/branch-menu/). Los estados como 429 o 503 están en [Estados que el contrato no documenta](/es/design/branch-other-status/).

### Desde el panel del paso

<Steps>
1. Haz clic en el paso, en el lienzo. Su panel se abre a la derecha.
2. Bajo **Si responde con error**, abre la lista junto al estado, por ejemplo **404**.
3. Elige la acción.
</Steps>

![La sección Si responde con error de createOrder: 400 sin acción, 401 Terminar el workflow, 409 Ir a «List products» y 429 Reintentar (hasta 3 veces)](/media/es/design-error-actions.webp)

<video controls muted playsinline preload="metadata" poster="/media/es/design-errors.webp" src="/media/es/design-errors.mp4"></video>

Luvin la escribe en el archivo con el nombre `on404`:

```yaml
onFailure:
  - name: on404
    type: end
    criteria:
      - condition: $statusCode == 404
```

Cada acción que defines también te da una prueba: Luvin genera un caso que simula esa respuesta y comprueba que la acción se active. Consulta [Casos](/es/test/cases/).

<Aside type="tip" title="Cambia el límite de reintentos">
**Reintentar** escribe `retryLimit: 3` y `retryAfter: 1` (segundos). Para usar otros números, cámbialos en la pestaña YAML, o guarda la acción como [reutilizable](/es/design/reusables/): su panel tiene ambos campos.
</Aside>

En esta sección pueden aparecer dos cosas más:

- Un grupo **Reutilizables** al comienzo de la lista, cuando una acción guardada maneja ese estado. Al elegirlo se aplica el reutilizable.
- La línea **Hay 2 acción(es) de error con criterios propios.** con **Editar en el YAML**. Esas acciones no dependen de un solo estado, por ejemplo dependen de un campo de la respuesta. El panel no las edita.

### Un paso nuevo para un error

A veces un error necesita su propia llamada, por ejemplo para listar Pokémon cuando no se encuentra la especie. **+ Un paso nuevo…**, en el menú de la tarjeta, abre un diálogo con la paleta, con el título **Paso nuevo si responde 404**. El paso que eliges queda al final del workflow, el error salta a él con una acción `on404` de tipo `goto`, y el último paso del camino feliz recibe una acción de éxito llamada `done` que termina la ejecución antes del paso nuevo.

[Un paso nuevo para un error](/es/design/branch-new-step/) muestra todo el recorrido, el YAML antes y después, varios pasos de rama y cómo deshacerlo. Para agregar un paso en otro lugar del workflow, usa el **+** de las flechas entre pasos: mira [Insertar un paso](/es/design/insert-step/).

Ejemplos ejecutables: [Reintenta, salta y termina ante errores](/es/recipes/error-branches/) y [Demostrar que la API rechaza datos inválidos](/es/recipes/expected-error/).

## Reintentos y llamadas lentas

### Qué hace un reintento

Cuando un paso no tiene éxito y su acción es **Reintentar**, Luvin envía el paso otra vez. Cada intento aparece en los resultados como, por ejemplo, **Reintento 1 de 3 (acción "on429")**. Si el último intento también falla, los resultados dicen **Se agotaron los 3 reintentos** y el paso falla.

| Ajuste | Comportamiento |
|---|---|
| Cuántas veces | `retryLimit`. Si una acción no lo tiene, Luvin reintenta una vez. |
| Cuánto esperar | `retryAfter`, en segundos, entre intentos. |
| Límite con la API real | <Badge text="Máx. 10 s" variant="caution" /> Luvin nunca espera más de 10 segundos entre dos intentos, aunque `retryAfter` sea mayor. |
| Simulación | No espera nada. |
| De dónde sale la espera | Solo de `retryAfter`. Luvin no lee un header `Retry-After` de la respuesta. |

### Ejecuta otro paso o workflow antes del reintento

Una acción `retry` también puede nombrar algo que se ejecuta primero. Luvin lo ejecuta una vez y luego llama otra vez al paso que falló. Sirve para renovar un token: la llamada responde 401, corre un login y se vuelve a intentar.

<Tabs>
  <TabItem label="Paso: stepId">

```yaml title="retry-step.arazzo.yaml" {5-6}
onFailure:
  - name: loginAndRetry
    type: retry
    stepId: login
    retryLimit: 2
    criteria:
      - condition: $statusCode == 401
```

Luvin ejecuta el paso `login` del mismo workflow. El paso tiene que existir: si no, el análisis dice **La acción "loginAndRetry" (retry) apunta al paso inexistente "login".**

  </TabItem>
  <TabItem label="Workflow: workflowId">

```yaml {4}
onFailure:
  - name: renewToken
    type: retry
    workflowId: $sourceDescriptions.auth.login
    retryLimit: 2
    criteria:
      - condition: $statusCode == 401
```

Luvin ejecuta el workflow, de este archivo o de otro archivo Arazzo, y guarda sus outputs para que el paso reintentado los lea.

  </TabItem>
</Tabs>

En los resultados, el intento aparece como **Reintento 1 de 2: antes corre el paso "login" (acción "loginAndRetry")**. El paso o workflow que corre primero cuenta para `retryLimit`, y Luvin espera `retryAfter` antes de cada reintento.

Ejemplo ejecutable: [Vuelve a iniciar sesión y reintenta](/es/recipes/retry-step/).

### Corta una llamada lenta con `timeout`

Un paso puede llevar un `timeout`, en milisegundos. Si la API no responde en ese tiempo, Luvin corta la llamada y el paso falla con **La API no respondió en 3000 ms (timeout del paso).** El panel del paso no tiene un campo para esto. Escríbelo en la [pestaña YAML](/es/design/arazzo-editor/), dentro del paso:

```yaml
steps:
  - stepId: getOrder
    operationId: $sourceDescriptions.shop.getOrder
    timeout: 3000
```

Mira [Motivos de falla](/es/reference/failure-reasons/) para saber cómo leer el mensaje. Para un paso que espera un mensaje, `timeout` significa otra cosa: mira [Pasos de mensajería](/es/design/messaging/).

## Mira las acciones en el lienzo

Activa **Acciones según la respuesta**, junto a **Mostrar:** sobre el lienzo. Cada tarjeta recibe una sección, **Si falla**, con una fila por respuesta:

| Fila | Significado |
|---|---|
| `404 → pokemonNotFound` **fin ✕** | Ante un 404, la acción `pokemonNotFound` termina el workflow. |
| `429 → on429` **reintenta ×3** | Ante un 429, el paso se intenta de nuevo hasta 3 veces. |
| `409 → on409` **ir a getOrder** | Ante un 409, la ejecución salta al paso `getOrder`. |
| `500 → sin acción` **falla** | El contrato documenta un 500 y nada lo maneja. |

Un salto también se dibuja como una línea naranja punteada que sale de la fila, recorre el lado izquierdo de las tarjetas y entra al paso de destino. Su etiqueta es el estado y el nombre de la acción. En la leyenda, el punto naranja es **salta a otro paso**. Para apartar una línea de salto de las demás, arrastra su tramo vertical hacia un lado; el cursor muestra **Arrastra para mover la línea**. Las líneas de datos se mueven igual.

Desactiva el interruptor para ocultar la sección y las líneas de salto cuando quieras leer solo los datos.

![El lienzo con Acciones según la respuesta encendido: la fila 409 de createOrder salta a listProducts y una línea naranja punteada sube por la izquierda hasta ese paso](/media/es/design-jump-line.webp)

## Comprueba que cada respuesta tiene manejo

La pestaña **Resumen** del workflow tiene una sección, **Cobertura de respuestas**, que compara el contrato con el workflow.

<Steps>
1. Abre la pestaña **Resumen**.
2. Abre **Cobertura de respuestas**. Su insignia dice, por ejemplo, **5/7 manejadas**.
</Steps>

La tabla tiene una fila por paso y estado documentado:

| Manejo en el Arazzo | Significado |
|---|---|
| ✓ **Éxito** | El estado es el que el paso espera. |
| ✓ **Acción** | Una acción lo maneja. Sigue el nombre de la acción. |
| ✕ **Sin manejo** | Nada lo maneja. Si la API responde esto, el workflow falla con un error genérico. |

No tienes que manejarlo todo. Maneja los errores que tu aplicación trata distinto, como «no encontrado» o «no aprobado».

![Cobertura de respuestas con 7/11 manejadas: una fila por paso y status, con Éxito, Acción o Sin manejo](/media/es/design-coverage.webp)
