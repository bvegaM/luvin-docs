Un contrato dice dónde vive la API (`servers`) y cómo está protegida (`security` y `securitySchemes`). Luvin no guarda direcciones ni secretos en los archivos de workflow. Convierte estas dos partes del contrato en las **URLs base** y las **Credenciales** de cada ambiente, así el mismo workflow puede correr contra un sandbox, un servidor de pruebas o producción.

## Ejemplo: el contrato de PayPal

El `paypal-orders.openapi.yaml` incluido declara un servidor y un esquema de seguridad para todas las operaciones:

<Tabs>
<TabItem label="Contrato">

```yaml title="paypal-orders.openapi.yaml"
servers:
  - url: https://api-m.sandbox.paypal.com
    description: Sandbox
components:
  securitySchemes:
    oauth2:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: https://api-m.sandbox.paypal.com/v1/oauth2/token
          scopes: {}
security:
  - oauth2: []
```

</TabItem>
<TabItem label="Ambiente">

```text title="Ambiente · URLs base"
paypal    Del contrato
https://api-m.sandbox.paypal.com
En un request: {{paypal}}/…
```

```text title="Ambiente · Credenciales · 0/1 completas"
oauth2    oauth2
Access token de OAuth2 (se envía como Bearer) · fuente paypal
```

</TabItem>
</Tabs>

La URL base se llama `paypal`, el nombre que el archivo de workflow le da al contrato. La credencial lleva el nombre del esquema, `oauth2`. Los pasos que llaman a PayPal van al sandbox y envían ese token, salvo que la pestaña **Autorización** del workflow diga otra cosa. El ejemplo de PayPal configura **OAuth 2.0** ahí, así Luvin pide y renueva el token por sí mismo. Mira [OAuth 2.0](/es/authorization/oauth2/).

## De servers a URLs base

Cada contrato OpenAPI que nombra un archivo de workflow recibe una fila en la sección **URLs base** de cada ambiente, con la etiqueta **Del contrato**. Luvin la completa con el primer servidor del contrato:

| En `servers` | URL base |
|---|---|
| `https://pokeapi.co/api/v2` | `https://pokeapi.co/api/v2` |
| `https://{region}.example.com/v1` con `variables: { region: { default: eu } }` | `https://eu.example.com/v1` |
| `/api/v2`, en un contrato descargado desde `https://example.com/specs/api.yaml` | `https://example.com/api/v2` |
| Varios servidores | Solo el primero. Escribe los otros en otros ambientes. |
| Sin `servers` | Vacía. El editor muestra *No define servers: la URL base se toma del ambiente.* |

Luvin completa una URL base solo cuando el ambiente no tiene una para ese contrato. Nunca sobrescribe un valor que escribiste. Así que:

- Cambiar `servers` en el contrato no cambia los ambientes que ya tienen la URL base. Cámbiala en cada ambiente.
- Un ambiente nuevo recibe el servidor del contrato.
- Si eliminas el último ambiente, Luvin crea uno vacío, de nuevo con los servidores de los contratos.

La URL base también funciona como variable en requests sueltos: `{{pokeapi}}/pokemon/pikachu`. Mira [URLs base](/es/environments/base-urls/) y [Ambientes](/es/environments/overview/).

### Qué dirección usa una llamada

| Situación | Dirección |
|---|---|
| El ambiente tiene una URL base para el contrato | Esa URL base, seguida de la ruta de la operación. |
| La URL base está vacía en el ambiente | El primer servidor del contrato. |
| No existe ninguna de las dos | El paso falla con *No hay URL de servidor para la fuente "x". Defínela en la pantalla de parámetros.* **Probar sola** avisa antes de enviar. |
| La operación, o su ruta, declara sus propios `servers` con una dirección completa | Esa dirección, diga lo que diga el ambiente. |
| La operación declara un servidor relativo, como `/uploads` | Se agrega a la URL base del ambiente. |

<Aside type="caution">
Una operación con su propio servidor completo, como `https://uploads.example.com`, ignora el ambiente. Úsalo para una operación que de verdad vive en otro host, y recuerda que cambiar de ambiente no la mueve.
</Aside>

Los contratos AsyncAPI también tienen servidores, pero son brokers (Kafka, MQTT…). Luvin los muestra en la vista previa y no los usa: los pasos de mensajería siempre se simulan. Mira [Contratos AsyncAPI](/es/contracts/asyncapi/).

## De security a credenciales

Una operación está protegida cuando tiene `security`, o cuando el contrato tiene `security` en la raíz y la operación no lo reemplaza. Una operación con `security: []` está abierta, aunque la raíz diga otra cosa. Si `security` lista varias alternativas, Luvin usa la primera que no está vacía y envía todos sus esquemas.

Por cada esquema que usa un paso de un workflow, la sección **Credenciales** del ambiente tiene un campo. Muestra el nombre del esquema, su tipo y la fuente, y cuenta cuántos están completos, por ejemplo *0/1 completas*. Un esquema que ningún paso usa todavía no aparece.

| `type` del esquema | El campo pide |
|---|---|
| `http` con `scheme: bearer` | *Token Bearer (se envía como Authorization: Bearer …)* |
| `http` con `scheme: basic` | *usuario:contraseña (se codifica en Base64)* |
| `apiKey` | *API key*, que se envía en el header, el parámetro query o la cookie que nombra el contrato |
| `oauth2` | *Access token de OAuth2 (se envía como Bearer)* |
| `openIdConnect` | *Access token de OpenID Connect (se envía como Bearer)* |
| Cualquier otro, como `mutualTLS` | *Tipo de seguridad no soportado; se ignorará* |

Cuando dos contratos usan el mismo nombre de esquema, el campo muestra primero la fuente: `paypal · oauth2`. Cómo viaja cada tipo, y qué hacer con los tokens de OAuth 2.0, está en [Credenciales del contrato](/es/authorization/contract-credentials/).

Cuando ningún contrato declara `securitySchemes`, la sección dice *Los contratos no declaran securitySchemes. Si la autenticación va en headers o en un paso del workflow, se toma de los inputs.*

## Dónde aparece la seguridad

| Lugar | Qué hace ahí la seguridad del contrato |
|---|---|
| Ejecuciones contra la **API real** | Los pasos protegidos envían las credenciales del ambiente activo. |
| La pestaña **Autorización** del workflow | **Del contrato** es la opción por defecto: *El contrato pide oauth2. Se usan las credenciales configuradas en el ambiente «ambiente».* Sin esquemas: *El contrato no declara autenticación para esta API.* Mira [Autorización de un workflow](/es/authorization/workflow/). |
| La pestaña **Casos** | **Sin credenciales**: se ejecuta sin ellas y espera `401` o `403` del primer paso protegido. Mira [Schemas, inputs y casos](/es/contracts/schemas-and-cases/). |
| **Probar sola** | *Faltan credenciales en «ambiente»: la API probablemente responderá 401.*, o *Se envían las credenciales del ambiente (nombres).* |
| Swagger UI | Para los esquemas API key, bearer y basic, **Authorize** viene completo con los valores del ambiente. Mira [Probar una operación](/es/contracts/try-it-out/). |
| Mock servers | Una ruta cuya operación documenta `401` responde `401` cuando faltan las credenciales. Mira [Credenciales y errores](/es/mocks/auth-and-errors/). |
| El análisis | Un header obligatorio que lleva la credencial, como `Authorization`, no se informa como faltante en el paso. |

<Aside type="note">
En **Simulación** nada sale de tu computador, así que las credenciales nunca se envían ni se necesitan.
</Aside>
