A contract says where the API lives (`servers`) and how it is protected (`security` and `securitySchemes`). Luvin does not keep addresses or secrets in the workflow files. It turns these two parts of the contract into the **Base URLs** and the **Credentials** of each environment, so the same workflow can run against a sandbox, a test server or production.

## Example: the PayPal contract

The bundled `paypal-orders.openapi.yaml` declares one server and one security scheme for every operation:

<Tabs>
<TabItem label="Contract">

```yaml title="paypal-orders.openapi.yaml"
servers:
  - url: https://api-m.sandbox.paypal.com
    description: Sandbox
components:
  securitySchemes:
    oauth2:
      type: oauth2
      flows:
        clientCredentials:
          tokenUrl: https://api-m.sandbox.paypal.com/v1/oauth2/token
          scopes: {}
security:
  - oauth2: []
```

</TabItem>
<TabItem label="Environment">

```text title="Environment · Base URLs"
paypal    From the contract
https://api-m.sandbox.paypal.com
In a request: {{paypal}}/…
```

```text title="Environment · Credentials · 0/1 filled"
oauth2    oauth2
OAuth2 access token (sent as Bearer) · source paypal
```

</TabItem>
</Tabs>

The base URL is named `paypal`, the name the workflow file gives the contract. The credential is named after the scheme, `oauth2`. Steps that call PayPal go to the sandbox and send that token, unless the workflow's **Authorization** tab says otherwise. The PayPal example sets **OAuth 2.0** there, so Luvin requests and renews the token by itself. See [OAuth 2.0](/authorization/oauth2/).

## From servers to base URLs

Every OpenAPI contract that a workflow file names gets a row in the **Base URLs** section of each environment, labelled **From the contract**. Luvin fills it with the first server of the contract:

| In `servers` | Base URL |
|---|---|
| `https://pokeapi.co/api/v2` | `https://pokeapi.co/api/v2` |
| `https://{region}.example.com/v1` with `variables: { region: { default: eu } }` | `https://eu.example.com/v1` |
| `/api/v2`, in a contract downloaded from `https://example.com/specs/api.yaml` | `https://example.com/api/v2` |
| Several servers | Only the first one. Write the others in other environments. |
| No `servers` | Empty. The editor shows *No servers defined: the base URL comes from the environment.* |

Luvin fills a base URL only when the environment has none for that contract. It never overwrites a value you wrote. So:

- Changing `servers` in the contract does not change environments that already have the base URL. Change them in each environment.
- A new environment gets the server of the contract.
- If you delete the last environment, Luvin creates an empty one, again with the servers of the contracts.

The base URL also works as a variable in single requests: `{{pokeapi}}/pokemon/pikachu`. See [Base URLs](/environments/base-urls/) and [Environments](/environments/overview/).

### Which address a call uses

| Situation | Address |
|---|---|
| The environment has a base URL for the contract | That base URL, followed by the path of the operation. |
| The base URL is empty in the environment | The first server of the contract. |
| Neither exists | The step fails with *There is no server URL for source "x". Set it on the parameters screen.* **Try alone** warns before you send. |
| The operation, or its path, declares its own `servers` with a full address | That address, whatever the environment says. |
| The operation declares a relative server, such as `/uploads` | It is added to the base URL of the environment. |

<Aside type="caution">
An operation with its own full server, such as `https://uploads.example.com`, ignores the environment. Use it for an operation that really lives on another host, and remember that switching environments does not move it.
</Aside>

AsyncAPI contracts have servers too, but those are brokers (Kafka, MQTT…). Luvin shows them in the preview and does not use them: messaging steps are always simulated. See [AsyncAPI contracts](/contracts/asyncapi/).

## From security to credentials

An operation is protected when it has `security`, or when the contract has `security` at the root and the operation does not override it. An operation with `security: []` is open, even if the root says otherwise. If `security` lists several alternatives, Luvin uses the first one that is not empty, and sends every scheme in it.

For each scheme that a step of a workflow uses, the **Credentials** section of the environment has a field. It shows the name of the scheme, its type and the source, and counts how many are filled, for example *0/1 filled*. A scheme no step uses yet is not listed.

| `type` of the scheme | The field asks for |
|---|---|
| `http` with `scheme: bearer` | *Bearer token (sent as Authorization: Bearer …)* |
| `http` with `scheme: basic` | *user:password (Base64 encoded)* |
| `apiKey` | *API key*, sent in the header, query parameter or cookie the contract names |
| `oauth2` | *OAuth2 access token (sent as Bearer)* |
| `openIdConnect` | *OpenID Connect access token (sent as Bearer)* |
| Anything else, such as `mutualTLS` | *Unsupported security type; it will be ignored* |

When two contracts use the same scheme name, the field shows the source first: `paypal · oauth2`. How each type travels, and what to do for OAuth 2.0 tokens, is in [Credentials of the contract](/authorization/contract-credentials/).

When no contract declares `securitySchemes`, the section says *The contracts do not declare securitySchemes. If authentication goes in headers or in a workflow step, it is taken from the inputs.*

## Where security shows up

| Place | What the contract's security does there |
|---|---|
| Runs against the **Real API** | Protected steps send the credentials of the active environment. |
| The workflow's **Authorization** tab | **From the contract** is the default: *The contract asks for oauth2. The credentials set in the «env» environment are used.* Without schemes: *The contract declares no authentication for this API.* See [Authorization of a workflow](/authorization/workflow/). |
| The **Cases** tab | **Without credentials**: runs without them and expects `401` or `403` from the first protected step. See [Schemas, inputs and cases](/contracts/schemas-and-cases/). |
| **Try alone** | *Credentials are missing in “env”: the API will probably answer 401.*, or *The environment credentials are sent (names).* |
| Swagger UI | For API key, bearer and basic schemes, **Authorize** comes filled with the values of the environment. See [Try one operation](/contracts/try-it-out/). |
| Mock servers | A route whose operation documents `401` answers `401` when the credentials are missing. See [Credentials and errors](/mocks/auth-and-errors/). |
| The analysis | A required header that carries the credential, such as `Authorization`, is not reported as missing in the step. |

<Aside type="note">
In **Simulation** nothing leaves your computer, so credentials are never sent and never needed.
</Aside>
